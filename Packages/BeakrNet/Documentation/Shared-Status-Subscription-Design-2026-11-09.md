# Foreground peer status subscription — bounded design

November 9, 2026. **Design subsequently authorized and implemented November 9; see the implementation/evidence section below. No live subscription testing yet.** The user authorized this read-only design phase after accepting the permission-lifetime increment. R1 and that accepted increment retain their documented scope. Numerical limits below are proposed policy, not benchmark results.

## Recommendation

Add one foreground monitoring view that explicitly starts and stops a leased subscription to the existing restricted SharedStatusSnapshot. Reuse authenticated selected-network transport and the established saved-permission/response-commitment rules. Implement this as a small app-owned service, not a generic subscription framework. It is periodic status monitoring, not CPU/memory/network profiling or a hard real-time service.

First scope: one outgoing subscription and one incoming subscription per selected runtime, potentially to different peers. Multiple windows observe the same runtime-owned subscription; closing the initiating view stops it. A second start for another peer returns busy rather than silently replacing the first. Existing one-shot status requests and Shortcuts remain independent.

## What exists, and what does not

| Area | Implemented foundation | Proposed addition |
| --- | --- | --- |
| Data | Version, sampled time, runtime state, authenticated-peer count | Repeated samples of exactly these fields |
| Transport | Authenticated Data envelopes, ephemeral expiry, route/session binding | A separate subscription operation namespace over the same connection |
| Permission | Fixed status-read permission with authority/credential pins and profile-scoped persistence | Separate default-off permission for periodic status access |
| Lifecycle | Runtime stop/disconnect invalidates capabilities; saved intent survives | Ephemeral subscription task, lease, sequence and acknowledgement state |
| Evidence | Accepted bounded one-shot and lifetime work; PL-1 deterministic ordering tests | No subscription tests, UI or delivery evidence yet |

The current SharedStatusClient accepts one correlated response/application error, not a stream. The responder supports only beakr.status/read/v1. Do not turn a one-shot correlation into an indefinite stream or grant periodic access from the existing read toggle.

Blackboard was assessed using Blackboard-Replication-Design.md. Its bounded subscriptions are hints to fetch canonical replicated state, with causal records, journals and synchronization. This proposal has no replicated records, history or replay, so reusing its repository machinery would add unrelated semantics. Reassess Blackboard if a later goal is shared synchronized state rather than transient samples.

## Permission and identity

Use a new fixed product permission, provisionally beakr.status.monitor/subscribe/v1. It authorizes only this snapshot and fixed service limits. One-shot read permission neither implies nor is implied by monitoring permission. Monitor start/renew require the monitor grant; stop and acknowledgements for an already bound session must remain possible without that grant, after authenticating the peer.

Reuse profile/network/local-node/remote-node scope, authority/environment/credential/key pinning, offline intent editing, stale-command revisions, failure handling, and interrupted-session confirmation. Do not migrate or reinterpret existing status-read grants. To bound persistence changes, use a separate profile-local monitoring-permissions file with the same writer semantics; any shared implementation must accept only a closed product-operation choice and validate the exact expected operation on load. Preserve the existing file's interpretation and schema. No arbitrary operation strings or general permission registry.

Enabling saved monitoring intent requires current verified membership and the selected local runtime; remote presence is unnecessary. Withdrawal remains possible while either profile or peer is offline. The grant is intent, not evidence of a live subscription.

Every sample must revalidate membership, current route/session and the saved grant. Sampling completion is not authorization. Each sample uses the accepted serialized commitment boundary: withdrawal first prevents commitment; an already committed sample is in flight and may arrive afterward. Permission withdrawal cancels future sampling/renewal and ends the subscription. Credential replacement/revocation/authority changes invalidate it under the existing policy. No subscription resumes automatically after a new grant.

## Lifetime and state

Subscription identity binds a fresh UUID to network, local/remote nodes, current runtime generation and authenticated route/session. IDs are identifiers, not credentials. Persist only permission, never subscription IDs, lease deadlines, tasks, counters or connected state.

| Event | Subscriber behavior | Responder behavior |
| --- | --- | --- |
| Explicit Start | Starting; bounded request deadline | Validate grant/binding/capacity, accept lease or return bounded error |
| Accepted start | Active; await initial sample | Schedule immediate first sample, then fixed cadence |
| Explicit Stop / initiating view closes | Immediately stop presenting incoming updates; send best-effort stop | Cancel sampling and release active slot on authenticated stop |
| Local runtime stops, iOS backgrounds, or selected network changes | End; invalidate ID and clear active tasks | End all subscriptions owned by that runtime |
| Peer disconnect / route replaced | End; show disconnected and last value as stale | End; do not restore on a new route |
| Reconnect | Available to Start again; no automatic restart | New Start and fresh authorization required |
| Grant withdrawn / trust unavailable | End or receive bounded termination reason | Block future commitments, cancel sampling |
| Lease or acknowledgement deadline expires | End on local deadline; no retry loop | End and release active capacity |

Foreground means the existing runtime is allowed to operate. iOS background stop remains unchanged. On Mac, merely moving focus to another app does not itself require termination; the initiating monitoring view must remain open and the selected runtime active. No keepalive exemption or new background execution entitlement is proposed. When the responder itself stops, delivery of a final stopped sample is not guaranteed; the subscriber shows disconnected/stale rather than inventing a remote state.

## Protocol and limits

Use a distinct versioned Data namespace, provisionally beakr.status.monitor. Product messages: start, renew, stop, sample, sample-ack, ended. Start/renew use bounded request-response control exchanges; sample and sample-ack use ephemeral messages with explicit subscription UUID and sequence. Do not alter generic DataMessage kinds or the existing status-read operation. Define and test a strict operation/kind matrix; unknown versions/types are rejected.

| Rule | Proposed first-increment limit |
| --- | --- |
| Sampling cadence | Fixed 2 seconds; no requester-selected rate |
| Lease | 30 seconds, measured locally with a monotonic clock |
| Renewal | Every 10 seconds while active; one pending control request |
| Control timeout | 10 seconds; failed renewal ends locally, responder expires independently |
| Outstanding samples | One awaiting application-level sample-ack per subscription |
| Slow receiver | Skip sampling ticks while awaiting ack; never queue missed ticks |
| Ack timeout | 10 seconds from sample commitment; timeout ends subscription |
| Buffering | One in-flight sample and one displayed last snapshot; no pending history |
| Payload | Retain status limits: 4 KiB body / 8 KiB envelope ceiling |
| Freshness display | Stale after 6 seconds without a new sample, immediately on known disconnect/stop |
| Active capacity | One incoming and one outgoing subscription per runtime |
| Duplicate control cache | At most 64 entries; retain through 30-second lease horizon; reject new admission if full |

A transport submission result is not proof that the subscriber consumed a sample. Explicit sample-ack gives the flow-control signal. The subscriber acknowledges only validated samples for the active ID/session, using strictly increasing sample sequence numbers. Duplicates are not redisplayed; a valid duplicate may be re-acknowledged. Future, malformed or wrong-binding acknowledgements cannot release the outstanding sample. When an ack arrives after skipped ticks, wait for the next scheduled tick; no catch-up burst.

Lease expiry at the responder is authoritative. Subscriber uses a conservative local lease deadline anchored to request start, not a remote wall-clock timestamp; renewals use unique correlations and strictly increasing renewal generations. Duplicate control requests return the original outcome without extending a lease. A stopped/expired ID cannot be renewed or restarted: bounded tombstones/duplicate records reject it for the maximum valid envelope lifetime, and envelopes expire within that same horizon. A fresh explicit Start uses a new ID. A new route has a new binding and cannot accept old messages. No durable delivery, offline spool, retransmission loop or replay.

Check local subscription generation/state after every suspension. Start/renew completion after local Stop is ignored; any accepted remote lease then ends by best-effort stop or expiry. Late samples after local Stop are discarded. The best-effort ended message contains only a bounded reason, not another snapshot, and its absence must not prevent local timeout cleanup.

Use local monotonic receive age for stale/timeout calculations; remote sampledAt is labeled as remote time, never used as a trusted freshness clock. Display sequence gaps as skipped updates if useful, not lost historical records. This is periodic best-effort monitoring, with no hard latency guarantee. Instrument counts and durations without payload values; idle/no-subscription must create no sampling/renewal timer.

## UI

In device details, add a separate periodic-status permission control and Start Monitoring / Stop Monitoring actions with explicit direction. Do not rename or overload the accepted one-shot controls. Show starting, monitoring, stale, stopped or disconnected; retain only the latest snapshot in memory with its remote sampled time and local age. Missing measurements are unavailable, never zero. If another view owns the outgoing session, show that fact and its shared state rather than starting another loop. No chart/history/export in this increment.

## Affected components and bounded sequence

1. New app-owned protocol/client/responder types for monitoring; reuse the snapshot schema and existing envelope/authenticated-binding conventions. No changes to the one-shot wire contract.
2. Extend the app permission implementation only enough to support two closed operation choices and two separately validated files; retain existing status-read fixtures as regressions. Reuse the PL-1 commitment primitive for each sample.
3. Add a runtime-owned subscription coordinator to ApplicationLANRuntimeManager composition and lifecycle callbacks. Explicitly dispatch both status namespaces before inbox handling; consume monitor messages without chat persistence or durable ACK. Unknown monitor operations must not fall through into chat.
4. Expose immutable monitoring state and start/stop commands through NodeBootstrapModel. Add the minimal details UI. Lifecycle, not view rendering, owns sampling and renewal tasks.
5. Verify with injected clocks, scheduling gates, signed membership fixtures and bounded transports on the authorized baseline simulator, then Xcode BuildProject. Any live phase is separately scoped and user-operated after fresh environment and loaded-build checks.

## Acceptance criteria

- Default-off monitor grant denies Start even if one-shot sharing is On; monitor permission does not enable one-shot reads. Persistent files and grants cannot cross operations, profiles, identities or authority changes.
- Start produces only the existing restricted snapshot; second concurrent Start is bounded; duplicate starts/renewals are idempotent without extending deadlines.
- Fake-clock tests prove cadence, expiry, renewal, stale presentation and no wakeups when inactive. Backpressure holds one sample, skips ticks and terminates at the ack deadline without memory growth or catch-up bursts.
- Stop immediately ends local consumption. Disconnect/background/profile switch cancels tasks and requires explicit fresh Start after reconnect. Old IDs/routes, delayed start responses and out-of-order samples cannot revive state.
- Deterministic gates prove withdrawal before sample commitment suppresses it, withdrawal after commitment permits at most the already in-flight sample, and slow transport does not delay withdrawal. Save failure/recovery and credential/trust invalidation block new samples.
- Integration tests prove monitoring messages never enter chat storage or cause durable ACK, and the accepted one-shot/Shortcuts path remains intact.
- UI distinguishes saved grant, active session and stale/offline state; permission remains editable under the existing offline rules. Focused tests and Mac/iPhone builds pass; evidence identifies fixtures versus live observations.

## Exclusions and review outcome

No background networking, automatic grants/resumption, simultaneous multi-network participation, arbitrary queries, cryptographic zero knowledge, general Actor delegation, AI interpretation, new transport/socket, metric collection/profiling, durable telemetry/history, remote configuration, Watch transport, or universal subscription framework.

Recommendation: approve this design as the basis of one separately authorized implementation phase. The design choices above are concrete defaults, not implementation approval. No code, builds, tests, device interactions or identity/profile operations occurred during this review. Earlier accepted work is not reopened.

### Implemented ownership and behavior

- SharedStatusRuntime owns one StatusMonitor for its selected runtime; ApplicationLANRuntimeManager supplies existing authenticated route resolution, immediate ephemeral submission, membership snapshot and restricted status sampler. Runtime invalidation/disconnection/trust callbacks stop subscription state. No second networking stack or new background capability.
- A closed StatusPermissionOperation enum distinguishes read and monitor. The coordinator keys stores by profile and operation. Existing shared-status-permissions.json retains its interpretation; status-monitor-permissions.json stores monitor grants separately and validates their fixed operation. Both stores use the same authority/credential pins, revision checks, atomic writes, recovery guard, retirement and serialized commitment rules. The one-shot runtime explicitly requires the read operation. Offline withdrawal and verified-membership offline enablement are retained.
- The wire namespace is beakr.status.monitor version1, with start/renew request-response controls and stop/sample/ack/ended ephemeral messages. The stored permission is beakr.status.monitor/subscribe/v1. The body carries a subscription UUID, sequence, optional restricted snapshot, and a bounded ended reason (currently stopped). The strict kind/body matrix, payload limits, expiry and source/destination/network/session/route validation reject malformed or mismatched traffic. The namespace is consumed before chat storage; it does not request durable ACK.
- One incoming and one outgoing subscription are admitted per runtime. Lease30s, renewal10s, control/ack timeout10s, sampling cadence2s and stale threshold6s use local monotonic time. No sample backlog: one sample awaits explicit application ACK; ticks are skipped while waiting. No automatic reconnect/resume or missed-sample replay. Duplicate controls return their original response without extending the lease; renew generations are checked. Control results and terminal IDs share a 64-entry ceiling (one slot reserved for active-session retirement). A Stop that overtakes Start leaves a tombstone; expired ACKs cannot revive a session. Old routes and late responses do not revive local state.
- Sampling and lease/renewal maintenance are runtime-owned tasks; no sampling/renewal timer exists without an active subscription. Permission observation uses an event stream, not polling. Stop/disconnect/invalidation cancels the relevant work. Transport cancellation remains best effort and cannot retract an already submitted envelope; ignored late controls expire by lease/deadline.
- Every sample rechecks current permission before the same serialized commitment primitive used by one-shot status. Withdrawal before commitment suppresses it; a committed sample may arrive afterward. The one-outstanding-sample rule bounds that in-flight exception per subscription. A slow transport does not delay withdrawal.
- Periodic Status controls appear alongside Shared Status in device details/presentation: a separate outgoing-sharing toggle, Start/Stop, session ownership across views, latest snapshot, remote sampled time, local age and stale/disconnected states. Closing the initiating view stops its session. Owner IDs are scoped to each observation generation so cancellation of an old view task cannot stop a replacement session. No chart, metric collection or historical archive. UI text and presentation have compiled but are not visually accepted yet.
- Diagnostics expose bounded counts for active/retained state, committed samples and skipped ticks; MONITOR logs contain profile/subscription IDs, event labels, counts and sampling-to-commit duration, never snapshot payloads. These are diagnostic observations, not performance guarantees.
